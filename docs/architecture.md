# Architecture

WhyDiff is a Python monorepo with a deliberately small dependency direction:

```text
CLI ─────┐
MCP ─────┴──> whydiff-core ──> database adapter ──> DuckDB
                       │
                       └──> typed findings and reports

dbt ──> dbt-generated SQL ──> dbt adapter
          └── conceptual contracts and parity fixtures <──> whydiff-core
```

## Boundaries

`whydiff-core` owns database-agnostic Pydantic contracts, deterministic diagnostic logic,
and the adapter interface. Models contain no connection or database-dialect behavior.

CLI and MCP translate their inputs to core contracts and serialize core results. Their SQL
execution always routes through the core adapter, keeping both runtime interfaces behind the
same validation, timeout, result-limit, and audit policy.

The dbt integration is intentionally a SQL-only package with no Python or `whydiff-core`
runtime dependency. It executes SQL generated by dbt macros through the configured dbt
adapter. The dbt package maintains conceptual contract compatibility and fixture parity with
core diagnostics, but it does not share the core execution path.

## Secure execution

Adapters accept one parsed read-only query. SQL that writes data, changes schema or session
state, attaches databases, loads extensions, performs external file/network scans, executes
dynamic SQL, or contains multiple statements is rejected before execution. Identifiers are
quoted component-by-component; data values use bound parameters.

DuckDB files are opened read-only when they already exist unless the caller explicitly
chooses otherwise. Audit metadata contains only a query fingerprint, statement type,
timing, row count, and truncation status—never SQL text, values, credentials, or paths.

## Compatibility

The public models and adapter APIs are shared across independently shipped interfaces.
Additive fields must have safe defaults. Removing fields, changing serialized enum values,
or narrowing accepted inputs requires a major version and migration guidance.
